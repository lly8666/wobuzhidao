# P5 >=30 minute soak candidate

- Date: 2026-09-21
- Authority before write: `734374c5f9a4b185d28fa28ae6d492c6700b42ff`
- Scope: new-version soak only
- Production FEC: off
- Padding: off

## Isolation

Two independent GitHub Actions jobs are used, one seed per VM/artifact. A job runs exactly one 31 minute soak scenario. 50/100 Mbps exploration, FEC profile selection and padding enablement are not mixed into this atom.

## Scenario

- duration: 31 minutes
- one-way delay: 300 ms
- deterministic packet loss: sustained 5% in both directions
- logical lanes: Game=2
- automatic same-ID lane rotation: every 60 seconds
- replacement grace: 3 seconds
- application: one real inner TLS 1.3 / HTTPS Connection: close flow every 10 seconds
- response sizes: 1 KiB / 8 KiB / 32 KiB cycle
- seeds: 20260935 and 20260936

Initial lanes are admitted before the loss injector is armed. Every automatic replacement after the measurement starts is therefore exercised through the sustained-loss network.

## Stop-flow retirement

Every HTTPS slot creates a distinct platform TCP BusinessFlow. After that request returns (success or finite-loss failure), the harness requires all of the following to converge before continuing:

- client TCPFlows == 0
- server TCPFlows == 0
- client TunnelOwner BusinessFlows == 0
- server TunnelOwner BusinessFlows == 0

A timeout here is a hard soak failure rather than being hidden by the final cleanup.

## Rotation

The final client and server generation maps are compared with the initial maps. At least 15 generation advances must be observed on both endpoints, and the final state must converge to exactly two active/two physical lanes with no retiring lane.

Transient failed rotation candidates are recorded as lifecycle_error evidence; they are not automatically promoted to a product failure if the old generation remains usable and business continuity/rotation progress remain valid.

## Memory plateau

Resource samples are taken every two seconds. The validator derives the minimum HeapInuse sample for each minute, then compares:

- middle window: minutes 10..19
- late window: minutes 21..30

The late median floor may not exceed the middle median floor by more than max(8 MiB, 50%). This is a bounded-state/leak gate, not a cross-run performance ranking. CPU, PPS and memory absolute values remain observational because hosted Actions VM capacity varies.

## Other evidence

The same run also records:

- raw pre-injection PCAP and outer/TLS-like events
- deterministic drop provenance and actual loss count
- injection queue residency and peak depth
- app success/loss/duplicate, RTT p50/p95/p99 and send lag
- host/per-core CPU, HeapAlloc/HeapInuse/Sys, GC count/pause
- inner TLS and outer wire rates / amplification
- final FEC/padding state

Finite random-loss request loss is reported; corruption, duplicates, prolonged business interruption, unbounded state, flow retirement failure, broken lane convergence or capture/injection inconsistency are hard failures.
