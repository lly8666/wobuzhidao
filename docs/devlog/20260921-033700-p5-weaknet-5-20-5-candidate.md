## Atom boundary

This candidate implements only the first prescribed P5 weak-network scenario:

- 300 ms one-way delay;
- 120 s measurement window;
- phases 30 / 60 / 30 s;
- injected outer drop 5% -> 20% -> 5%;
- real inner TLS 1.3 HTTPS through the formal `runtimeentry -> TunnelOwner -> Normal lane -> platformflow` path.

It does not include 5% -> 30% -> 5%, load qualification, >=30 min soak, FEC tuning, padding enablement, classifier work, or performance parameter selection.

## Fixed FEC / padding policy

The formal product default is still FEC off. The previous 20:10 atom qualified one explicit capability/cost point only and did not select a production weak-network profile.

Therefore this atom keeps one fixed policy for the entire scenario:

- FEC: `off`;
- padding: `0/off`.

There is no FEC sweep, adaptive profile, or parameter competition.

## Outer weak-network injection

The injector is a hosted `SegmentIO` seam placed after synchronous outer capture and immediately before the peer `memorySegmentEndpoint` delivery. It therefore acts on the formal runtimeentry/Tunnel/lane outer traffic, while capture loss and injected network loss remain separate.

Both c2s and s2c directions use:

- fixed 300 ms queue delay;
- phase-clock-driven drop policy;
- deterministic per-direction/per-phase packet ordinals;
- independent run seeds `20260921` and `20260922`;
- raw queue enter/leave timestamps, residency, depth/peak, drop decision, score, actual packet length, phase, and seed.

Dropped packets are not inferred from application timeouts; the raw network-decision stream is the authority for injected drop counts.

## Workload and post5 definition

The workload schedules one real HTTPS request every 3 s on an absolute application clock, with a controlled 1 KiB / 8 KiB / 32 KiB response-size cycle. Actual send lag is recorded. No transport batching wait or fixed sleep is used to gather packets.

Each scheduled request has a bounded deadline and records:

- scheduled/actual phase;
- BusinessFlowID;
- inner TLS 1.3 handshake timing;
- HTTP request start/complete timing;
- request/response RTT sample;
- response bytes and SHA-256;
- inner TLS ciphertext bytes;
- explicit failure stage when a request does not complete.

Application duplicates are independently checked from target-server request ordinals.

The predeclared post5 recovery metric is:

> time from the 90 s transition into the final 5% phase until completion of the third consecutive successful scheduled HTTPS request in that final phase.

The validator recomputes this from raw request samples. A run without that recovery condition does not qualify.

## Raw evidence and resource sampling

The existing P5 recorder remains authoritative for raw outer PCAP plus packet/TLS-like-record JSONL, including direction, lengths, intervals, and burst accounting.

The weak-network atom additionally saves:

- `requests.jsonl`;
- `network.jsonl`;
- `resources.jsonl`;
- `manifest.json`;
- validator `summary.json`;
- test log.

Existing active-tree primitives are reused for transport retransmit/abandon/outstanding stats, BusinessFlow counts, padding, and lane FEC inventory. The only new observation seam is low-frequency harness-side resource sampling of:

- Go memory / GC counters;
- Linux `/proc/stat` aggregate and per-core CPU counters;
- injection queue depth/peak;
- outer counters/bytes;
- transport outstanding/retransmit state.

PPS and CPU busy ratios are recomputed by the validator from raw counters; queue residency is recomputed from delivery timestamps.

## Independent validator

`tools/check_p5_weaknet_measurement.py` does not trust the harness summary. It recomputes or cross-checks:

- 30/60/30 phase order/timestamps and 5/20/5 configured drop;
- every deterministic drop decision and actual drop count/ratio by phase/direction;
- 300 ms queue residency and queue peaks;
- PCAP packet count versus raw outer-packet events;
- raw packet/record directions, lengths, intervals, and bursts;
- scheduled HTTPS application loss and duplicate counts;
- RTT p50/p95/p99 from raw samples;
- post5 recovery from raw success/failure sequence;
- FEC-off inventory, FEC recovery=0, padding=0, repair retransmits separately;
- wire amplification from raw network packet lengths and raw inner TLS byte counts;
- resource sample coverage, CPU busy, memory/GC, queue, and phase PPS.

Application loss is measured rather than silently forced to zero in this lossy scenario; corruption, duplicate application delivery, malformed provenance, or missing recovery evidence is a hard failure.
