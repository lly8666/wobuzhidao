## Active-tree FEC policy audit

The formal executable entry points were inspected before choosing a P5 FEC-on scenario.

At the base HEAD:

- `cmd/wbd-client/main_linux.go` has no FEC flag;
- `cmd/wbd-client/main_windows.go` has no FEC flag;
- `cmd/wbd-server/main_linux.go` has no FEC flag;
- their `ClientLaneParams` / `ServerLaneParams` leave `ParityShards` at the Go zero value;
- therefore the actual formal entry is currently **FEC off**;
- the project documents preserve the fixed family `off,20:4,20:8,20:10,20:12,20:16,20:20` but do not select one non-zero production default.

Accordingly this atom does not claim that any non-zero profile was already a production default, and it does not perform a profile sweep or selection contest.

## Minimal explicit configuration

The candidate adds one operator-visible flag to the formal client/server entry points:

`--fec-parity`

with:

- default `0` = FEC off;
- accepted values only `0,4,8,10,12,16,20`;
- no dynamic/adaptive profile;
- no extra flush/buffer tuning flags.

When non-zero FEC is explicitly enabled, the candidate uses the active-tree timing/bound already used throughout the qualified FEC fixtures:

- partial block flush: 8 ms;
- decoder heavy-block bound: 8.

Those values are centralized as runtime defaults. Production behavior remains off unless the operator explicitly chooses a fixed profile.

## Runtime timer gap found during P5 audit

The lane-level FEC implementation already has `FlushDue`, but the formal `runtimeowner.Runtime.Tick` at the base HEAD only runs repair/ACK timing and did not call lane `FlushDue`.

That means a partial FEC block on an otherwise idle formal runtime could retain sources without emitting its due parity.

The candidate closes only that wiring gap:

1. `TunnelOwner.TickLane` operates on one authoritative lane incarnation;
2. it calls the existing lane `FlushDue`;
3. due parity records are generation-fenced;
4. `runtimeowner.Runtime.Tick` sends those records through the existing lane transport;
5. retiring incarnations continue repair tick but cannot create new FEC parity;
6. RX FEC/LINK expiry is driven by the same owner tick.

No FEC coding algorithm, profile geometry, wire format, recovery horizon, or transport repair algorithm is redesigned.

If optional padding is ever enabled later, timer-generated parity may use existing record padding budget but does **not** add useful-payload credit, preserving the P4 rule that FEC amplification cannot earn more padding allowance. This P5 atom keeps padding off.

## FEC inventory observability

The candidate adds read-only counters only:

Encoder:

- systematic source shards emitted;
- parity shards emitted;
- full blocks;
- partial blocks;
- pending source count.

Decoder:

- Reed-Solomon reconstruction events;
- reconstructed source count.

The latter counters increment only when `codec.Reconstruct` actually returns previously undelivered source payloads. A systematic-only completed block is not labeled as FEC recovery.

These counters are exposed through the existing lane/path stats snapshots; no per-packet logging is added.

## Controlled P5 scenario

The new measurement uses one explicit fixed profile:

`20:10`

This is chosen as a single controlled capability/cost scenario because the active FEC package already names parity 10 as `WeakParityShards`. It is **not** a product recommendation, selection result, or production default.

Scenario:

- one real inner TLS 1.3 full HTTPS connection;
- one BusinessFlow;
- one already-established outer Normal lane;
- controlled Root -> Intermediate -> leaf certificate verification;
- 256 KiB response body, enough to exercise full FEC blocks;
- no network loss injection;
- padding `0/off`;
- production outer repair remains enabled but is required to stay unused in this lossless run;
- condition-driven wait until both encoders report zero pending sources.

The harness requires both directions to emit source and parity shards and requires at least one full server-side FEC block.

## Cost and loss accounting

Raw artifacts continue to save:

- outer PCAP;
- outer packet events;
- TLS-like record events;
- HTTPS flow event;
- FEC inventory event;
- manifest;
- validator summary;
- test log.

Loss/cost fields remain separate:

- capture loss;
- injected network drop;
- FEC reconstruction/recovered sources;
- runtime repair retransmits;
- padding bytes;
- application loss/duplicate.

For the no-loss atom all recovery/repair/drop/padding counts must be zero even though FEC parity is actually emitted.

Wire amplification is recorded as a reproducible ratio:

`steady outer IPv4/TCP bytes / inner TLS ciphertext bytes`

with numerator and denominator stored separately. The validator recomputes the ratio from those byte inventories.

This is cost evidence only; the atom makes no performance or traffic-analysis conclusion.
