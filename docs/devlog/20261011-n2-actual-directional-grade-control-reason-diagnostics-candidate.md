## Why change
Existing production diagnostic `LaneDiagnostic.parity_shards` is the *initial immutable 20:20 admission envelope*, not the newly selected TX parity. The controller only publishes one read-only decision through a test-compatible accessor. A waveform test observing a green 10Mbps application flow could incorrectly claim automatic downshift without any proof. Add low-rate **opt-in only** sampled N2 controls to the ordinary existing diagnostic JSONL; do not add per-packet event logging, timer, pcap storage or extra control traffic.

- Active/retiring `runtimeentry.LaneDiagnostic.actual_tx_parity` explicitly comes from live `LaneStats.TxPath.ParityShards`; keep original `parity_shards` as negotiated fixed max and maintain server per-client separation.
- `runtimeowner.ControlStats` supplies bounded active-incarnation only fields: N2 controller enabled, latest actually authenticated same-TX-source report sequence and generation, accepted decision reason, ordinary vs aggressive advised profile, source count/shape/confidence/bound width, decision version/unix ns and pending state; all optional and gathered only on `ControlStats` diagnostics read under the existing `laneTransport.mu`. UNKNOWN/HOLD remains its own reason; no zero-loss lie.
- Add real `N2CommittedSwitches` and `N2BusyHolds` per-incarnation counters only within the short commit path, to avoid confusing a proposed lower档 with an applied profile. On the existing directed active owner/Tick lower, check opt-in stats show 20→4 actual commit reason LOWER and exactly one completed switch, no outstanding control signal. These fields are not wire/GUI changes.
